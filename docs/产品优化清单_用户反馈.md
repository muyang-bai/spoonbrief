# 用户反馈优化清单（v2，方向已确认，实施中）

> 反馈来源：真实用户使用反馈（4 项）
> 状态：**方向已与产品负责人确认，进入实施**
> ✅ 已拍板：统一扣费+默认额度 60 ｜ 订阅级月度上限 ｜ 先扩内置源（自定义源下期） ｜ 时+分双下拉框（秒固定0）

---

## 反馈一：时间选择控件别扭（下拉选择，去掉秒）

### 现状
- 三个滑杆：时（0-23）/ 分（0-59）/ 秒（0-59）+ 每天/每周/每月分段
- cron 以 6 字段存储（秒在最后），后端已兼容

### 问题分析
- 滑杆拖 0-59 找分钟很费劲，触屏更难
- 秒级精度对简报场景无意义（cron 秒字段恒为 0 即可）

### 方案
1. 时间控件改为 **时、分两个下拉框**（时 00-23 全列；分 00-59，滚动选择）
2. 秒固定为 0：前端 buildCron 直接拼 0，后端解析保持兼容（历史 6 字段数据不受影响）
3. 频率保持现有分段（每天/每周/每月），每周需选星期几、每月需选几号（下拉化同样处理）
4. 额外加分项：时间下方实时预览"下次发送：xx 月 xx 日 xx:xx（北京时间）"（现在已有预览，保留）

### 工作量：小（前端 1 个文件为主）｜优先级 P0

## 反馈二："立即生成"改为"立即推送"

### 问题分析（用户语义很准）
- 新手视角：这个产品 = 抓资讯 → 分析 → **推送给我**。"生成"是内部动作，用户不关心"生成"，关心"送到我手里"
- 动词应该与用户心智一致：**推送**

### 方案（全站统一语义）
| 位置 | 现在 | 改为 |
|---|---|---|
| 订阅卡片按钮 | 立即生成 | **立即推送** |
| 成功 toast | 报告已生成并发送 | **简报已推送，请查收邮箱** |
| 失败 toast | 报告生成失败 | **推送失败**（原因附后） |
| 历史报告页标题 | 历史报告 | 历史简报（可选，一并统一） |
| 落地页演示台 | 生成我的简报 | 保留"生成"（那是演示"生成过程"，语义正确） |
| 邮件主题 | 科技情报 - 日期 | 不变（已是"简报"语境） |

### 工作量：极小（纯文案，2-3 处）｜优先级 P0

## 反馈三：额度不透明、无法管理（重点，详见专项分析）

### 用户到底在说什么（三种场景叠加）

**场景 A：免费用户怕"突然就没额度了"**
平台给每个用户月度额度（现默认 30），用户不知道：
- 每份简报消耗多少额度（1 次 AI 分析 = 1 额度）
- 自己一堆订阅加起来每月消耗多少（例：3 个每日订阅 = 90/月 > 30 额度）
- 剩余额度什么时候用完、用完会怎样（现状：手动触发直接报错拒绝，定时不受影响——规则不一致）

**场景 B：自带 API Key 的用户在花自己的真金白银**
用户配置自己的 DeepSeek/火山 Key 后，**每次定时简报都在消耗他自己 Key 的余额**。订阅在后台自动跑，用户忘了关订阅 = 持续扣钱。这就是"要是忘记了就白白花钱"的直接场景——钱是用户的，平台目前没有任何预算提示。

**场景 C：未来商业化预演**
产品将来若按量收费/售卖额度，用户需要：创建时知道成本、按订阅分配预算、超支自动止损。现在不做，付费上线时就是事故。

### 结论
用户要的不是"免费给更多额度"，而是**消耗可预期、可预算、可封顶、可提醒**——本质是"费用管理"能力。

### 方案（分三层，从轻到重）

**第一层：透明化（P0，必须做）**
- 创建/编辑订阅弹窗内显示：
  - 单份消耗：1 额度（平台 Key）或"消耗你自有 Key 的余额"（自带 Key 时）
  - 按频率折算：每月预计消耗 X 额度（每天=30、每周≈4、每月=1）
  - 当前账户剩余额度 + 重置日期
- 订阅卡片显示该订阅的"月消耗预估"小字
- "我的画像"页已有额度展示，补一个"全部订阅合计月消耗 vs 剩余额度"的进度条

**第二层：预算管控（P1，推荐做）**
- 订阅新增字段 `monthly_quota`（可选，默认不限）：该订阅每月最多消耗 N 额度
  - 生成前校验：本订阅本月已用 N → 自动跳过本次并邮件通知"订阅 X 本月额度已用完，已暂停/等待下月"
  - 可选"耗尽后自动停用订阅"开关
- 账户级提醒：剩余额度 < 20% 或 < 5 份时，简报邮件底部加提醒行 + 站内公告
- 生成失败原因里明确写"额度不足"，不再让用户懵

**第三层：计费规则理顺（P1，需要产品决策）**
- 现状不一致：手动"立即推送"扣额度，定时发送不扣。**必须统一**：
  - 方案 1（推荐）：所有路径统一扣额度，同时把默认额度从 30 上调到 60，保证免费体验
  - 方案 2：只有自带 Key 用户才涉及计费，平台 Key 完全不扣——免费期简单，但商业化时要重构
- 决策后，deps.check_api_quota 与定时链路统一走同一套扣费/校验函数

### 工作量：第一层 小；第二层 中（模型+API+前端）；第三层 小但需拍板｜优先级 P0+P1

## 反馈四：信息源更多 / 支持用户自己添加

### 现状
- 内置 12 个 RSS 源（IT之家、财新、开源中国、36氪快讯等），管理后台可增删改
- 用户端"信息源"页只读浏览；用户不能添加
- 信息池是"平台源 → 池 → 关键词过滤"架构：**池子里没有的领域，关键词再准也匹配不到**

### 方案（分两步）

**第一步：内置源扩编（P1）**
候选（需逐个验证 RSS 可用性 + 版权合规）：
- 科技：机器之心、虎嗅、晚点 LatePost、InfoQ、差评
- 财经：华尔街见闻、每日经济新闻、界面新闻
- 综合：澎湃新闻、观察者网、新华网科技
- 注：聚合类源以官方 RSS/公开接口为准，正文仅存摘要（当前架构已如此）

**第二步：用户自定义信息源（P2，价值高但工作量大）**
- 用户可添加自己的 RSS 地址 → 进入**个人源池**（仅该用户的简报使用，不进公共池，避免投毒/版权风险）
- 新增表 user_news_sources + 添加/删除/校验 API + 订阅创建时可勾选"包含我的信息源"
- 抓取调度：随订阅生成时按需抓取（个人源量小，不必常驻 30 分钟轮询）
- 安全：URL 校验（http/https）、超时限制、内容大小限制、失败不阻断主流程

### 工作量：第一步 小-中；第二步 中-大（模型+抓取+前端+测试）｜优先级 P1（第一步）/ P2（第二步）

## 风险与注意事项

- cron 数据兼容：去秒后历史 6 字段数据必须能继续正常解析（后端已兼容，前端 parseCron 需容错）
- 额度统一扣费后，老用户可能突然收到"额度不足"——需提前公告 + 默认额度上调
- 新信息源逐个验证 RSS 稳定性，失败的源要有自动降级（现状已有 sources_failed 机制）
- 用户自定义源需限制抓取频率与内容长度，防 SSRF/滥用
